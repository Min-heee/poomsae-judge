# 따라하기 게임 PRD — 교본 오버레이 · 판정 카드

> `docs/PRD.md` 와 같은 9절 구조이고, **이번에도 구현 전에 먼저 커밋합니다.**
> 범위는 세 가지(교본 오버레이 · 따라하기 게임 · 결과 카드)뿐이며 **판정 규칙은 한 글자도 바꾸지 않습니다.**

## 1. 한 줄 정의와 문제

**화면이 교본 자세를 제시하고, 제한 시간 안에 그 자세를 만들면 이미 있는 판정 코어가 점수를 내고, 그 결과를 한 장의 이미지로 남기는 놀이 층입니다.**

지금 앱은 판정을 잘 설명하지만 **판정을 받으러 가는 길이 없습니다.** 무엇을 해야 하는지 아무도 말해 주지 않기 때문입니다. 그래서 셋을 보탭니다 — 할 일을 보여 주는 **교본**, 시간 안에 해 보게 만드는 **루프**, 결과를 들고 나갈 **한 장**.

## 2. 목표와 비목표

### 목표

- 카메라 없이도 세 기능을 전부 시연할 수 있다. 샘플 재생이 여전히 기본 모드다.
- 게임 점수는 **기존 감점에서만** 유도된다. 새 채점 규칙을 만들지 않는다.
- 어긋남을 실시간으로 보이되, 화면의 기존 색 뜻을 흔들지 않는다.
- 결과 카드에 **사람을 식별할 수 있는 것은 한 점도 넣지 않는다.**
- 303 테스트 통과, 샘플 7종 점수 불변, First Load JS 200 kB 이하.

### 비목표

- **품새 한 벌**(태극 1장 24동작 같은 연속 진행). 동작 단위라는 경계를 그대로 지킨다.
- **여러 사람 동시 플레이, 온라인 랭킹, 서버 저장.** 서버가 없다는 것이 이 프로젝트의 구조다.
- **소리와 효과음.** 외부 에셋을 받지 않기로 했고, 코드로 합성하는 것은 이번 범위가 아니다.
- **새 동작 추가**와 **판정 규칙 변경.** 감점 값·경계값·보류 조건은 손대지 않는다.

## 3. 사용자와 시나리오

**심사위원(카메라 없음).** 홈에서 "따라하기 게임"을 누릅니다. 기본이 **시연 모드**라 카메라를 묻지 않습니다. [시작] → 교본 → 3·2·1 → 합성 샘플이 플레이어 입력으로 흘러 들어가 루프가 돕니다. 5라운드가 약 1분에 끝나고 카드가 뜹니다 — 클릭 세 번.

**수련생(카메라 있음).** [웹캠으로 하기]로 같은 루프를 몸으로 돕니다. 교본 고스트 위에서 **어긋난 관절이 빨갛게** 뜨고 옆에 `+12°` 가 붙습니다. **지도자**는 판정 화면에서도 같은 오버레이를 켜고 끕니다.

## 5. 설계 — 루프 · 오버레이 · 카드

### 5.1 게임 루프와 "판정 창은 과거를 본다"는 제약

한 판은 **한 코스 5라운드**, 코스는 **정면(주춤서기)** 과 **측면(앞차기)** 입니다. 동작을 섞지 않는 이유는 규칙이 카메라 각도를 전제하기 때문입니다(H6) — 섞으면 라운드마다 몸을 90° 돌려야 하고, 안 돌리면 전부 보류입니다.

| 단계 | 시간 | 하는 일 |
|---|---|---|
| 제시 | 1.5초 | 교본 스켈레톤과 한 줄("발을 조금 더 넓게") |
| 준비 | 3초 | 3·2·1 카운트다운. **아직 기록하지 않는다** |
| 맞추기 | 6 → 5.5 → 5 → 4.5 → 4초 | 시작 신호와 동시에 기록 시작. 오버레이가 실시간으로 뜬다 |
| 판정·피드백 | 2초 | 채택된 창을 되감아 재생 + 점수·감점 표시 |

하한 4초는 규칙에서 나옵니다. A5가 **0.8초 유지**를, H7이 **0.2초 이상 멈춘 구간**을 요구하고, 앉는 데 2초쯤 걸립니다. 4초 미만은 난이도가 아니라 **불가능**입니다. 라운드마다 0.5초씩 줄이는 것이 난이도 곡선이고, 규칙을 건드리지 않고 만들 수 있는 유일한 곡선입니다.

**판정 창이 과거를 본다는 제약은 두 겹으로 다룹니다.**

첫째, **기록기를 시작 신호에서 연다.** 웹캠 훅의 4초 링버퍼(`WINDOW_MS`)를 그대로 쓰면 카운트다운 중의 준비 자세가 버퍼에 남습니다. 게임은 별도 기록기로 시작 신호 이후 프레임만 담아 **준비 자세가 채점될 경로 자체를 없앱니다.** 입력 계층의 버퍼 문제이지 판정 규칙이 아닙니다.

둘째, **그 구간에서 가장 잘 맞은 창을 고른다.** 구간을 통째로 채점하면 자세로 들고 나는 전이 프레임이 중앙값을 끌어내립니다. 그래서 **창 2.0초를 0.2초 보폭으로** 밀며 각 창에 기존 `judgeSequence` 를 그대로 돌리고(6초면 후보 21개) **기본점이 가장 높은 창**을 채택합니다(동점이면 먼저 끝난 창). 2.0초는 A5의 0.8초와 앞차기 한 번(약 1.2초)을 모두 담습니다. 창마다의 판정이 평소와 똑같으니 규칙은 불변이고, **모든 창이 보류면 라운드도 보류입니다 — 점수를 지어내지 않습니다.**

### 5.2 점수 산식

판정 점수는 그대로 쓸 수 없습니다. 최대 감점이 주춤서기 1.3 / 앞차기 1.7이라 **점수 범위가 8.7~10.0**, 게임 점수로는 누구나 90점입니다. 그래서 **감점을 정규화**합니다.

```
기본점  = round( 100 × (1 − 총감점 ÷ 채점된 항목의 최대 감점 합) )   // 0~100
콤보배수 = 1 + 0.1 × min(연속 성공 수, 5)                          // 1.0~1.5, 성공 = 기본점 ≥ 70
속도점  = min(20, floor( (제한 시간 − 채택 창이 끝난 시각) × 4 ))   // 0~20
라운드 점수 = round(기본점 × 콤보배수) + 속도점                      // 0~170
```

분모는 **그 라운드에서 실제로 채점된 항목들의 major 감점 합**입니다(주춤서기 전부면 1.3). 항목 보류(H4)로 빠진 항목은 분자·분모 양쪽에서 빠집니다. 라운드 보류는 0점이고 콤보가 끊깁니다. 새 경계값은 하나도 없습니다.

**등급은 총점이 아니라 기본점 평균으로 매깁니다.** ★★★ 90, ★★ 75, ★ 60 이상, 그 아래는 별 없음. 별은 "얼마나 맞았나"만 말하고 콤보·속도는 점수판에만 보탭니다 — 잘 맞춘 사람과 빨리 맞춘 사람을 같은 별로 부르지 않으려는 것입니다. 화면과 카드에는 **10점 만점 원점수와 감점 목록을 함께** 띄웁니다.

### 5.3 교본 오버레이

**교본은 새 데이터가 아니라 기존 리그(`src/samples/rig.ts`)로 생성합니다.** 발 간격·무릎 내각·상체 기울기를 주면 33개 랜드마크가 나옵니다 — 내려받을 에셋이 0입니다.

**교본 값은 합격대의 한가운데로만 잡습니다.** 발 간격 2.00(합격 1.70~2.30), 무릎 내각 138°(합격 ≤145), 좌우 차 0°, 상체 0°. 문제마다 바꾸는 값도 합격대 **안에서만** 움직입니다(1.80 / 2.00 / 2.20). 교본대로 했는데 감점이 나오면 화면이 거짓말을 하는 것이기 때문입니다.

**정렬은 셋뿐입니다.** (1) 두 스켈레톤을 각자의 **어깨 폭 S로 나눕니다** — 키와 카메라 거리가 사라집니다. (2) **엉덩이 중점을 원점**으로 맞춥니다(world 좌표가 이미 그렇습니다). (3) 거울 변환은 그리기 직전 한 번만 걸리므로 교본도 같이 타고, 앞차기는 판정이 아는 차는 다리로 좌우를 뒤집습니다. **회전 정렬은 하지 않습니다** — 맞추면 규칙이 전제하는 카메라 각도(H6)가 흐려지기 때문입니다.

**색 규약. 뿌리는 한 줄입니다 — 점선은 "읽지 못했다", 실선은 "읽었다".**

| 무엇 | 표현 | 기존/신규 |
|---|---|---|
| 교본 고스트 | `--brand-dim` 반투명 실선, 관절은 빈 원 | 신규 |
| 흐린 관절(visibility < 0.5) | **빨강 점선** | **기존 그대로 — 바꾸지 않음** |
| 어긋남 15° 초과 | **빨강 실선 + 굵은 링 + `+12°` 라벨** | 신규 |
| 주의 6~15° | 노랑 실선 + 라벨 | 신규 |
| 6° 이내 | 평소 색(파랑·회색) | 기존 |

두 빨강은 **한 관절에 동시에 칠해질 수 없습니다.** 흐린 관절은 각도를 계산하지 않으므로(측정값이 없으므로) 어긋남 등급을 받을 수 없습니다 — 구조가 보장하는 배타입니다. 표현도 점선/실선으로 갈리고 어긋남에는 늘 숫자 라벨이 붙습니다. 범례는 상시 둡니다.

문턱 6°/15°는 **표시 전용**이며 감점을 만들지 않습니다. 근거는 기존 규칙표입니다 — A3가 8°/15°, A4가 10°/18°에서 등급을 가릅니다. 같은 대역을 쓰면 오버레이의 빨강과 판정 카드의 빨강이 **대체로 같은 관절을 가리킵니다** — 충돌을 피하는 대신 일치시키는 쪽입니다. 하한 6°는 H4의 ε(2°)의 세 배로, 검출 잡음이 색을 흔들지 못합니다.

### 5.4 결과 카드

**크기 1080×1350(4:5)**, 캔버스로 그려 `toBlob` → `<a download>`, 파일명 `poomsae-20260924-정면코스-812.png`. `navigator.share` 가 있으면 먼저 시도합니다.

담는 것: 코스 이름 · 총점 · 별 등급 · 라운드 5개의 미니 막대 · **가장 잘 맞은 라운드의 스켈레톤**(내 자세 + 교본 고스트) · 그 라운드의 10점 만점 원점수와 감점 두 줄(측정값·경계값 포함) · 날짜 · **규칙표 버전(`RULES_VERSION`)** · 입력원 · "공인 기준 아님" 한 줄.

**개인 식별 정보는 두 겹으로 막습니다.** (1) **영상 픽셀을 한 점도 넣지 않습니다** — 랜드마크 좌표에서 새로 그립니다. (2) **얼굴 랜드마크(0~10번)를 그리지 않습니다** — 머리는 원 하나입니다. 이름 입력칸도 없습니다. 입력원 표시는 샘플 점수를 자기 기록처럼 보이게 두지 않으려는 장치입니다.

### 5.5 시연 모드 (카메라 없는 사람)

게임의 **기본값**입니다. 플레이어 입력 자리에 합성 샘플을 흘려보낼 뿐, 루프·판정·오버레이·카드는 웹캠 모드와 **완전히 같은 코드**를 지납니다. 라운드별 샘플은 코스가 정해 둡니다(정면: 합격 · 좁음 · 합격 · 좁음 · 합격) — 점수가 오르내려야 콤보와 등급이 움직이는 것을 보입니다. 재생은 결정적이라 **몇 번을 눌러도 같은 결과입니다.**

## 6. 설계 결정과 대안 — 재미는 어디서 오는가

**손맛은 네 군데서 만듭니다. 코드로 그릴 수 있는 것만 적습니다.**

1. **즉각 피드백.** 맞추기 내내 어긋난 관절이 빨강↔노랑↔평소 색을 오갑니다. 몸을 움직이면 화면이 바로 답합니다 — 유일한 조작감입니다.
2. **카운트다운.** 숫자가 커졌다 작아질 뿐이지만, 시작 시점을 알려야 사람이 준비합니다.
3. **"가장 잘 맞은 2초" 되감기.** 5.1의 창 선택이 그대로 연출이 됩니다.
4. **모으는 맛.** 콤보 배수가 화면에 남고 끝에 카드 한 장이 떨어집니다.

**하지 않을 연출:** 소리, 파티클, 화면 흔들기. 별 채움 전이와 점수 카운트업만 CSS로 두고 `prefers-reduced-motion` 에서는 그마저 끕니다.

**왜 정규화했나.** 대안인 판정 점수 ×10 은 87~100점만 나와 변별이 없습니다. 정규화는 **기존 감점 값의 재표현**이고, 원점수를 함께 띄워 두 척도가 같은 사실을 말한다는 것을 보이게 했습니다.

**왜 별도 라우트(`/game`)인가.** 홈이 게임 화면과 카드 렌더러를 필요로 하지 않으니, 라우트를 가르면 홈의 First Load JS 가 그대로 남습니다. three.js 를 동적 import 로 뗀 것과 같은 이유입니다.

## 7. AI 코딩 툴 사용 방식

순서를 지킵니다 — **이 문서가 `feat/follow-game` 의 첫 커밋이고, 코드는 아직 한 줄도 없습니다.**

- **사람이 정한 것:** 단계별 시간과 하한의 근거, 점수 산식과 콤보·등급 문턱, 색 규약(점선/실선의 뜻), 카드에 넣을 것과 **넣지 않을 것**, 비목표.
- **AI에 맡길 것:** 캔버스 렌더링, 라운드 상태 기계, 카드 그리기, 테스트 확장, "문서가 약속한 것이 구현에 없는 곳"을 찾는 적대적 검토.
- **검증:** `npm run verify`, `npm run build`, 그리고 회귀 하나 — **샘플 7종의 판정 스냅샷이 전후로 동일할 것.** 판정을 건드렸는지는 기억이 아니라 테스트가 말합니다.

## 8. 리스크와 남은 일

- **슬라이딩 창의 비용.** 6초 구간이면 `judgeSequence` 를 21번 돌립니다. 순수 함수이고 창마다 60프레임이라 수 ms로 보지만 실측 전에는 추정입니다. 느리면 보폭을 0.4초로 늘립니다 — 창 선택의 해상도만 낮아지고 판정은 그대로입니다.
- **웹캠은 여전히 실기기로 확증하지 않았습니다.** 다만 시연 모드가 같은 코드를 지나므로 루프 자체는 카메라 없이 검증됩니다.
- **교본 파라미터.** 합격대 한가운데라는 규칙은 명확하지만, 그 값이 실제 도장의 교본과 같다는 보장은 없습니다. 유단자 검토 목록이 한 줄 늘었습니다.
- **남은 일:** 실기기 확증, 교본 파라미터 검토, 카드의 긴 라벨 줄바꿈, 측면 코스의 문제 변형 설계, 번들 실측(현재 131 kB / 한도 200 kB).
